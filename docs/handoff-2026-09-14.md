## What's real and verified vs. what's still a gap

**Verified live, end-to-end, on prismpublication.com** (not just locally): submission form → D1 → admin approve → `/run-ads/` match → labeled card render. Tested with real HTTP requests and a real browser session before and after each merge.

**Not built, and don't assume otherwise:**
- Approving a submission in `/admin/` does **not** add it to `sdk/catalog.json`. Those are two separate catalogs. A third-party publisher's SDK integration still reads only the static JSON file.
- No payment collection yet (see #8 above).
- No non-JS publisher integration path — `sdk/prismClient.js` needs a Node/JS server. `functions/api/match.js` is architecturally the right pattern for fixing this (plain HTTP, any language), but it currently serves `/run-ads/` against D1, not publishers against `sdk/catalog.json`.

## Guardrails that exist for a reason — read before you "fix" something

- **The homepage is frozen.** `index.html`, `css/styles.css`, `js/demo.js` — do not redesign, restructure, or re-theme, even if you think it's an improvement. Daniel has explicitly said this rebuild cycle needs to stop. If a task seems to need a homepage change, stop and ask.
- **No third-party services beyond what's already here** (PayPal, Cloudflare's own stack, Google Analytics). Resend and Supabase both caused real pain in earlier attempts — that's not superstition, it's the reason Cloudflare Pages Functions + D1 was chosen specifically.
- **Don't invent numbers.** Pricing, fill rates, visitor counts — none of it gets published without Daniel providing the real figure. This has come up multiple times this session and the answer is always the same.
- **Cloudflare Pages Functions, never a standalone Worker.** A past session tried deploying this as a separate Worker and it fought with Pages over routing on the same domain — that's why the README says "never `npx wrangler deploy`." `functions/` in this repo auto-deploys with the normal Git-connected Pages build; no CLI, no second deploy step.
