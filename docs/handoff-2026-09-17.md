## The repositioning that drove everything below

The niches (fitness/sleep/productivity, later fitness/travel/health-wellness) were an artifact of an earlier, abandoned MVP aimed at third-party chatbot developers -- categories were picked because those were topics people chatted about with bots. That MVP had zero real installs. The current MVP, confirmed directly: **the site's own phone UI, general-purpose like a normal AI chat, open to anyone who wants to run contextualized ads, sized for roughly 300–500 visitors, not a niche content play.** Niches are "nearly irrelevant" now. Ads still only show on real contextual match (unchanged 0.65 cosine floor); the assistant itself and the advertiser category field are not topic-restricted. Full planning record: [run-ads-strategy-2026-09-16.md](run-ads-strategy-2026-09-16.md).

## What actually happened today, in order

1. **Brought a Cowork strategy session into the repo** as [run-ads-strategy-2026-09-16.md](run-ads-strategy-2026-09-16.md) -- the planning record for everything below, including the original staged build plan (Prompt 1 inventory → Bridge → Stages 0–6).
2. **Stage 0 -- cleaned live-text contradictions.** Sleep tools and productivity were never Daniel's niches; fitness/travel/health-and-wellness went in briefly, then the category field was opened to free text entirely (see repositioning above) -- the real gate became the brand-safety rules, not a topic whitelist.
3. **Stage 2 -- general live chat on `/run-ads`.** Was an advertiser-only self-test page; now a real, general-purpose, ChatGPT-like chat open to any visitor, no account. Ads still only appear on contextual match. Answers come from Workers AI by default (`@cf/meta/llama-3.1-8b-instruct-fast` -- the non-`-fast` id is deprecated, cost real debugging time to find), or OpenAI if `OPENAI_API_KEY` is set -- Daniel flagged OpenAI is under real consideration for quality, so the provider choice is a one-file, one-env-var change (`functions/api/_lib/model.js`), not a rewrite.
4. **Stage 3 -- build an ad from a product URL.** Paste a URL on `/run-ads` → drafted card (brand/title/description/CTA/category) → edit → test free in the same chat, scored privately alongside the public pool → "Submit for review" prefills `/ad-submission/`. Safe URL fetch (`_lib/urlFetch.js`): https only, blocks localhost/private IPs, 12s timeout and 6MB cap (both raised from stricter starting values after Amazon and Shein product pages hit them on completely normal pages).
5. **Stage 4 -- light-touch automated screening.** Runs in `functions/api/submit.js`. Explicitly *not* the heavier rule-based version first built (price-text/ALL-CAPS/shortener detection) -- cut after direct feedback that false-positiving a real advertiser was worse than not having the checks; kept only the one hard, non-negotiable stop (the prohibited-category list already on `/ad-submission/`). Everything else -- health claims, uncertain cases -- routes to manual review in `/admin/` without blocking anyone. **Gambling correction, twice:** first written as a flat block (wrong), then as "blocked on wellness bots only" (also wrong -- that condition was pre-existing site copy nobody had actually decided, and stopped making sense once niches did). The real rule, confirmed directly: gambling is *permitted*, not blocked, but only with licensing, KYC compliance, and confirmed legality in the advertiser's state/country -- none of which ad copy can verify, so it always routes to manual review, never auto-clears or auto-rejects.
6. **Stage 5 -- free submission, prepaid click credit to go live.** The $5-at-submission fee is retired -- confirmed directly this is a real removal, not additive. Submitting and testing (both `/api/match` and the chat) are free. The only charge: once a submission is approved, the advertiser buys prepaid click credit on a token-based campaign page (`/campaign/:token` -- no account system exists, so this link is their only way back) to go live. Credit is billed per click, auto-deactivates on exhaustion. **Pricing is explicitly placeholder** (`functions/api/_lib/pricing.js`) -- not real numbers yet.
7. **A real production bug, found via Daniel's own testing, not caught in review:** the entire site's internal nav/footer links were hardcoded absolute URLs (`https://prismpublication.com/...`) instead of relative paths. Harmless in production, but it meant every click on a Cloudflare Pages *preview* deployment bounced the visitor straight to production -- which is what made testing this branch's work so confusing for most of a session before the cause was found. Fixed site-wide (306 links, 24 pages, canonical tags and JSON-LD left correctly absolute).
8. **A real deploy-model correction:** this Pages project runs **Build System v3**, which reads bindings (D1, Workers AI, etc.) straight from `wrangler.toml` in the repo -- confirmed directly via the dashboard refusing manual binding additions ("managed by Wrangler"). The opposite of what this repo's own docs claimed before today. New resource bindings go in `wrangler.toml` now, not the dashboard; secrets are still dashboard-only, under a different settings section than Bindings.

## What's real and verified vs. what's still a gap

**Merged to `main` and deployed to production.** Verified on the branch preview before merging: general chat answering for real, ad-from-URL drafting, the relative-links fix. Stage 5's billing logic (purchase → balance → click → auto-deactivate) was verified directly against production D1 after merging -- ran the exact SQL `credit/purchase.js` and `c/[id].js` execute, using a disposable test campaign, cleaned up after. All correct: no credit excludes from matching, a purchase includes it, each click deducts and the card deactivates exactly when the remaining balance can't cover one more click. **What's still unclicked**: an actual PayPal order create → approve → capture round-trip, since that needs a human in a browser (this environment can't reach `prismpublication.com` or PayPal's API at all to drive it, and PayPal fundamentally requires human approval regardless). Confirmed acceptable to ship without that click-through for now.

**Not built, and don't assume otherwise:**

- PayPal webhooks -- the credit-purchase flow reuses the existing direct-capture-and-verify pattern instead (same as the old $5 flow did).

- Credit balance/active-state visibility in `/admin/` -- nice-to-have, not required for the loop to work.
- Email notifications of any kind -- deliberately not added; the existing "no third-party service without asking" rule (below) blocked the original plan's "email Daniel a signed approve/reject link" step, and the token-based campaign page exists specifically to route around needing email for the advertiser side too.
- `docs/pricing.md` and `docs/ad-submission.md` -- already-stale operator docs describing an even older third-party-SDK sales motion, now further out of sync after Stage 5. Flagged repeatedly this session, never given the real rewrite pass it needs.

## Guardrails that exist for a reason -- read before you "fix" something

- **The homepage is still frozen** (`index.html`, `css/styles.css`, `js/demo.js`) -- this session touched `index.html` only for narrow, non-visual factual corrections (categories, gambling policy) via direct hrefs/text swaps, never structure or design. Anything beyond that still needs to stop and ask first.
- **No third-party services beyond what's already here** (PayPal, Cloudflare's own stack, Google Analytics, and now Workers AI / optionally OpenAI for the chat). This came up directly again this session (the email-notification step) and the answer was the same as 14 September: don't add one without asking.
- **Don't invent numbers or conditions.** Came up twice today, hard: the gambling "wellness bots" condition was never a real decision and got corrected twice before landing right; the two Stage 5 pricing constants are explicitly marked placeholder for the same reason. If you don't know the real answer, say so and ask -- don't fill the gap with something plausible-sounding.
- **Cloudflare Pages Functions via `functions/`, and now `wrangler.toml` is real** -- Build System v3 reads it for bindings on every Git-connected build, on whichever branch is building. Don't send anyone to the dashboard to add a binding by hand; add it to `wrangler.toml` and let it deploy. Secrets are still the dashboard's job.
